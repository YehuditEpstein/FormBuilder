# חלק 3 – ארכיטקטורה והבנת ענן (הכנה לתשובה בעל פה)

מסמך זה הוא תשתית הכנה לתשובות שיינתנו **בעל פה** בהקלטת המסך, כנדרש בהנחיות ההגשה.
הוא אינו תחליף להסבר המוקלט, אלא תמצית שאפשר להיעזר בה תוך כדי ההקלטה.

## שאלה 1: ארכיטקטורה ומיקום הרכיבים בענן (Hybrid Cloud)

**עקרון מנחה:** כל מה שחייב להיות חשוף לאינטרנט — ברשת ציבורית ומאחורי שכבת הגנה;
כל מה שמחזיק נתונים או לוגיקה פנימית — ברשת פרטית בלבד.

- **Angular (SPA)** – מתארח כ-Static assets על CDN / Blob Storage + Azure Front Door
  (או CloudFront). זהו הרכיב היחיד שבאמת "יושב" באינטרנט הפתוח.
- **.NET API** – רץ ב-App Service / AKS / Container Apps בתוך **VNet פרטי**. לא
  חשוף ישירות; נכנסים אליו רק דרך API Management / Application Gateway + WAF,
  שמבצעים TLS termination, authentication ו-rate limiting.
- **SQL (בענן)** – Azure SQL / Managed Instance עם **Private Endpoint** בלבד (ללא
  Public Access), בתוך אותו VNet או VNet מקושר (peering).
- **מסד הנתונים הפנימי (On-Premise)** – נשאר ברשת הארגון. אין לחשוף אותו
  לאינטרנט בשום צורה.

**חשוף לאינטרנט:** רק ה-Frontend הסטטי ונקודת הכניסה של ה-API Gateway/WAF.
**ברשת פרטית:** ה-API עצמו, מסד הנתונים בענן, וכל שירות פנימי נוסף.

**תקשורת מאובטחת מול הארגון (On-Premise):**
- **Site-to-Site VPN** או **Azure ExpressRoute / AWS Direct Connect** בין ה-VNet
  בענן לרשת הארגון — כך שהתעבורה בין הענן ל-On-Premise לא עוברת דרך האינטרנט
  הציבורי כלל.
- גישה הדדית מוגבלת ע"י **NSG / Firewall rules** לפי כתובות ופורטים ספציפיים בלבד
  (Least Privilege).
- **Mutual TLS (mTLS)** ואימות מבוסס **Service Principal / Managed Identity** לכל
  קריאה בין המערכות, בנוסף להצפנת התעבורה עצמה.
- Secrets (connection strings, מפתחות) מנוהלים ב-Key Vault ולא בקוד/בקונפיגורציה.

## שאלה 2: ארכיטקטורת GenAI לצ'אט לבניית HTML דינאמי

**רכיבים נדרשים ואחריותם:**

1. **Chat UI (Angular)** – מציג את השיחה ותצוגה מקדימה (preview) חיה של הטופס.
   שולח את הודעת המשתמש + מזהה השיחה (conversationId) לשרת. **לא** שולח prompts
   ישירות למודל השפה — כל תקשורת עם ה-LLM עוברת דרך ה-Backend.
2. **Chat/Orchestrator API (.NET)** – מקבל את הודעת המשתמש, טוען את ה-state
   הנוכחי של הטופס והיסטוריית השיחה, בונה prompt (system + context + היסטוריה
   מקוצרת/מסוכמת), קורא ל-LLM, ומוודא/מנקה את התוצאה לפני שהיא חוזרת ללקוח.
3. **LLM Provider** (למשל Claude/GPT) – מקבל prompt מובנה ומחזיר **ייצוג מבני
   (JSON schema של שדות)**, ולא HTML גולמי ישירות. ה-HTML עצמו נבנה בצד השרת/לקוח
   מתוך אותו ייצוג מבני, לפי אותם ה-Templates שמשמשים את ה-Form Builder הרגיל.
4. **Validation & Sanitization Layer** – שכבה ייעודית שבודקת את תשובת המודל מול
   JSON Schema קבוע מראש (שמות שדות מותרים, טיפוסים, גבולות אורך), ודוחה/מתקנת
   תשובה שלא תואמת. **לעולם לא** מריצים HTML/JS שחוזר מהמודל כפי שהוא.
5. **State Store (DB)** – שומר את מצב הטופס הנוכחי ואת היסטוריית השיחה לפי
   conversationId, כך שכל תור בשיחה הוא "state + הודעה חדשה" ולא כל ההיסטוריה
   הגולמית בכל פעם (חיסכון בטוקנים וב-context).

**זרימת המידע:** משתמש → Angular → Orchestrator API → (טוען state קיים) → בניית
prompt → LLM → תשובה כ-JSON מובנה → Validation/Sanitization → עדכון ה-state
במסד הנתונים → רינדור HTML מהייצוג המבני → מוחזר ל-Angular לתצוגה.

**ניהול State לאורך השיחה:** ה-state (הגדרת הטופס הנוכחית + מטא-דאטה של השיחה)
נשמר בצד השרת (DB), לא רק בזיכרון הדפדפן — כך שהשיחה ניתנת להמשך גם אחרי רענון
דף, וניתן לבצע Undo לגרסה קודמת של הטופס.

**איך מוודאים תקינות ובטיחות:**
- ה-LLM **לא** מחזיר HTML חופשי אלא ייצוג מבני מוגבל (allow-list של סוגי שדות),
  שממנו נגזר HTML קבוע-מראש (Template-based rendering) — כך אין הזרקת קוד אפשרית.
- אם בכל זאת יש רינדור HTML גמיש יותר: הרצה דרך **Sanitizer** (כגון DOMPurify)
  עם allow-list קפדני של תגיות/מאפיינים, והצגה בתוך `<iframe sandbox>` מבודד.
- הגבלת קצב (rate limiting) ו-Timeout על קריאות ל-LLM, ולוגים לביקורת (audit).

## שאלה 3: אינטגרציה בין המערכת החדשה (ענן) לישנה (On-Premise)

**גישה מומלצת: אינטגרציה מבוססת אירועים (Event-Driven), לא Polling ולא גישה
ישירה למסד הנתונים של הצד השני.**

- כאשר תבנית טופס נוצרת/מתעדכנת בענן, ה-API מפרסם אירוע (`FormTemplateCreated`)
  ל-**Message Broker** (Azure Service Bus / Kafka) שנגיש דרך ה-VPN/ExpressRoute.
- מערכת ה-On-Premise מריצה **Integration Adapter/Consumer** קטן שמאזין לאירועים
  אלו ומעדכן את מסד הנתונים הפנימי בהתאם — כל צד אחראי אך ורק על מסד הנתונים
  שלו (Data Ownership ברור, ללא כתיבה חוצת-רשתות ישירה).
- שימוש ב-**Outbox Pattern** בצד השולח (טבלת אירועים + פרסום אסינכרוני) מבטיח
  שאף עדכון לא "יאבד" גם אם התקשורת נופלת רגעית.
- לחלופין, במקרה של תלות בזמן אמת נמוכה יותר: חשיפת **API קריאה בלבד**
  (Read-only) מהענן, שהמערכת הפנימית קוראת ממנו דרך הערוץ המאובטח (VPN),
  עם Caching מקומי בצד ה-On-Premise כדי לצמצם תלות ברשת.
- בכל מקרה: **Schema Versioning** על מבנה האירוע/ה-API כדי שגרסאות ישנות של
  המערכת הפנימית ימשיכו לעבוד גם כשמוסיפים שדות חדשים לתבנית הטופס.
